Data contracts

Three shapes hold the whole system together. Get these right on Friday and the rest is mechanical.

Snapshot — the thing that gets hashed

Byte-reproducible or the project has no property worth demoing. Sorted keys, fixed decimals as strings, block pinned per chain, no wall-clock timestamp anywhere inside.

Register entry — one HCS message per run

Keep it under a few hundred bytes. The full snapshot is not stored; it is reproducible from the pinned blocks, which is the entire point.

MCP tools — the whole public surface

current_risk(chain?: string, minScore?: number)
  → { entrySeq, findings[], publishedAt }

changes_since(collateral?: string, window: "24h" | "7d" | "30d")
  → { changes[{ protocol, field, from, to, atBlock }] }

track_record(minScore?: number, since?: string)
  → { total, confirmed, missed, entries[{ seq, score, outcome }] }

track_record is the differentiator. The other two exist in tools the sponsor already links to.

III

The hourly run, with its failure branches

Every stage has a way of going wrong that produces a plausible-looking but worthless result. Those are the ones written out below.

  1. Scheduled transaction executes on Hedera The listener picks up the consensus event and immediately arms the next one, one hour out. If it fails Arm the next run before doing any work, not after. Otherwise one crash silently ends the clock and the register just stops — which looks exactly like hiding a bad call.
  2. Collector reads the current head block per chain and pins it Every subsequent query targets that block explicitly, not "latest". If it fails Querying "latest" across 90 deployments means each one answers at a different block. The snapshot becomes unreproducible and the verifier fails on your own data.
  3. Collector queries the standardized schema and canonicalises Sort keys recursively, format every number as a fixed-precision string, drop nulls, then hash. If it fails Floating point formatting differences between your machine and the verifier's produce a different hash for identical data. Serialise numbers as strings from the start.
  4. Evaluator client fetches encrypted thresholds and calls the enclave The model config is decrypted inside 0G, never in your process. If it fails If you decrypt thresholds locally and send them as a prompt, the model is not sealed and the whole claim collapses. This is the architectural line that must not be crossed.
  5. Attestation signature is verified before anything is written Check it against the enclave's public key, not just presence of the field. If it fails Write an entry marked attestation: failed rather than skipping the run. A gap in the register is indistinguishable from concealment.
  6. Registry writer submits one message to the HCS topic Sequence number, pinned blocks, both hashes, findings, attestation. If it fails Retry with the same sequence number. Never renumber — the sequence is what makes gaps visible.
  7. Outcome scoring runs on entries older than the evaluation window Compare each past finding against what the chain actually did, and write the outcome as a new entry referencing the old sequence number. If it fails Never mutate the original entry. Outcomes are appended, never edited — that distinction is the product.
