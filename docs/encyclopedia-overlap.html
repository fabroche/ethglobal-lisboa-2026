Overlap — the encyclopedia

Everything the product does, in the order it does it: first in plain words, then in code, with the file path for every snippet. Written to be studied before judging.

1 · How to use this

Every part of this document follows the same two-step shape:

A box like this explains what happens using no jargon at all. If you can say this part out loud, you can answer 80% of the questions you will be asked.

A box like this gives the mechanism: the algorithm, the data shape, the exact function. This is what you need when someone follows up with "but how?"

Code blocks always name their file, so you can open it while you read:

One rule for the whole document: nothing here is aspirational. If it says the code does something, the code does it today. Where a guarantee is not yet true, it is in §9 — What we prove, and what we don't. Read that section twice; it is the one that protects you.

2 · The mind map

Two people want to do a deal but neither will say their number first, because whoever speaks first loses ground. Overlap is a sealed room: both write their terms, nobody can read anybody else's, and a referee locked inside a machine that even its owner cannot open reads both and says one word — workable or not workable.

Three outside services make that possible. 0G is the sealed room the referee sits in. Hedera is the public noticeboard: it holds the deadline and the fingerprints of what was written, so nobody can change their mind afterwards. World makes sure each side is one person with one seat, so nobody opens ten rooms to guess your number.

Nine module libraries under src/, each behind a port so the SDKs stay at the edges: session, seal, worldid, registry, scheduler, evaluator, reveal, plus lib and config. The UI in src/app/ composes them; nothing in src/components/ ever imports an SDK. Environment variables are read in exactly one place, src/config/env.ts, validated with Zod and fail-fast.

3 · Keywords

Grouped by who owns the term. If someone uses one of these at you, this is the sentence to have ready.

The idea

The going-first problem
Whoever names a number first loses negotiating ground. It is why deals die before the first call, and it is the problem Overlap exists to remove.
Commitment
A fingerprint of what you wrote, published before anyone can see anything. You cannot change your position afterwards, because the fingerprint would no longer match. Integrity, not secrecy.
Sealing
Encrypting your position so nobody can read it while it waits. Secrecy, not integrity. Commitment and sealing are two different guarantees and you need both — one stops you changing your mind, the other stops anyone peeking.
The probing attack
Open ten rooms and binary-search the other side's number: "workable at 400k? at 420k?" Six rooms and you know their limit. World's one-seat-per-side is the control that kills it.
Leak budget
Every distinct thing the referee can say tells you something. Two possible answers leak almost nothing; one answer per possible reason would leak half the negotiation. The size of the output vocabulary is the privacy dial.
Fail closed
When something cannot be verified, produce nothing rather than something unverified. No valid attestation ⇒ no verdict, ever. The opposite (fail open) would make the guarantee decorative.

0G

TEE — Trusted Execution Environment
A region of a CPU isolated by hardware. The CPU encrypts that memory, so the operating system, the hypervisor and the machine's owner cannot read it. Not a promise not to look — an inability.
Intel TDX · dstack
The specific TEE technology 0G's provider runs (verifier-v0.5.5, read from the on-chain service record). TDX is Intel's confidential-VM technology; dstack is the framework around it.
Attestation
Evidence that a computation really happened inside a genuine enclave. Full attestation means parsing a hardware quote and walking a certificate chain to Intel. We do the last link only — see §9.
teeSignerAddress
The address of the key that lives inside the enclave and signs its responses. This is what OG_ENCLAVE_PUBKEY holds: 0x0038f716958a90b753da6937787395e2365db2e8. It is not the provider address (0x4870CbC4…), which is only who gets paid. Both are fields of the same on-chain struct, one index apart, and confusing them fails every verification with signer_mismatch.
Broker · Router
The broker is the provider's own endpoint, paid per request from our wallet. The Router (router-api.0g.ai) is a convenience gateway that pays the broker with its wallet — which is why a Router call can never yield a signature for us: the broker's customer is the Router, not Overlap. We go direct.
chatID
The handle a completed call is keyed by. You fetch the signature with it: GET {base}/v1/proxy/signature/{chatID}?model=…
Compute ledger
An on-chain account that pre-funds inference. Minimum 3 0G to open — an account floor, not a usage cost. A call is about 0.0005 0G.
TeeML vs TeeTLS
Two service modes. TeeML runs the model inside the enclave (what we need). TeeTLS terminates the TLS session inside it. 0G testnet has no model that is both a chatbot and TeeML — which is why we are on mainnet.
EIP-191 / personal_sign
Ethereum's message-signing framing: the bytes are prefixed with \x19Ethereum Signed Message:\n<len> before hashing. 0G signs this way; our scheme name for it is secp256k1-eth.

Hedera

HCS — Hedera Consensus Service
An append-only, consensus-ordered message log. You submit a message, the network agrees on its order and timestamp, and it can never be edited or removed.
Topic
One HCS log. Overlap uses a single topic for everything; messages carry a roomId so a reader can filter. This is our database.
Consensus timestamp · sequence number
Assigned by the network, not by us. The sequence number is why a missing message is detectable: a gap means somebody dropped something.
Mirror Node
The public REST read path. Anyone can replay our topic without asking our server — which is what makes "here is the receipt" credible rather than a screenshot.
Schedule Service
Hedera's native scheduled transactions. Our deadline clock. See §9 for what is and is not wired.
No Solidity
Three native services, zero contracts deployed. That is the track requirement and it is literally true of this repo.

World

World ID
A proof of personhood. Not a login — we never learn who you are.
Selfie Check
The credential we want: a face check, weaker than an Orb but far stronger than nothing. It is requested through IDKit 4.x only, as selfieCheckLegacy.
Nullifier
An opaque one-way value derived from (app_id, action, person). The same person verifying twice for the same action produces the same nullifier — which is how you detect a repeat without ever learning an identity. We store nothing else.
Action
The scope string the nullifier is derived under. Ours is per room and side: seam-<roomId>-<side>. Scope it per app instead and a person could use Overlap exactly once, ever.
IDKit
World's client widget. v2 exposes verification levels (orb, device); 4.x exposes credentials and requires a server-signed rp_context.
Cloud verify
Server-side proof verification. Client-side would be theatre — the client is the thing you do not trust.

Our stack

Next.js App Router · Server Components · Server Actions
Pages render on the server by default; a Server Action is a function the browser can call that only ever runs on the server. It is how the write screen submits a commitment without us shipping an API layer.
Zod
Runtime schema validation. Every external response — 0G, Hedera, World — is parsed through it at the boundary. TypeScript types vanish at runtime; Zod does not.
Ports and adapters
Each module declares a narrow interface (RegistryPort, SealedModel, WorldVerifier, ScheduleService) and the SDK lives behind it. That is why the logic can be tested without a wallet, a network or a single euro of spend.
ECIES
"Encrypt to a public key" done properly: generate a throwaway keypair, do ECDH with the recipient's public key, derive a symmetric key from the shared secret, encrypt with that. Detail in §7.
AES-256-GCM · AEAD
The symmetric cipher we encrypt with. AEAD means it also authenticates: modify one byte of the ciphertext and decryption fails loudly instead of returning garbage.
HKDF
Turns a raw ECDH shared secret into proper key material. Raw shared secrets have structure; cipher keys must not.
Canonical serialisation
Exactly one bytes-for-a-payload function, so a signer and a verifier on different machines agree byte for byte. Sorted keys, no whitespace, NFC strings, no floats. src/lib/canonical.ts is the single implementation, deliberately.
@noble/*
Audited, dependency-free crypto libraries. The signature check uses these and nothing from 0G's SDK — that is what makes it independent.

4 · The journey, step by step

01 Open the room Hedera

The person starting the deal picks what kind it is (property, job, OTC trade), sets a deadline, and gets two links. Before either link works, the deadline is written to Hedera's public log.

That order matters more than it looks. Because the clock is published before anybody can write a word, neither side can move it later, and neither side can wait to see what the other did. It is a referee's whistle nobody owns.

createRoom validates the input, asserts the deadline is in the future, generates a room id, publishes the expiry, and only then returns the join links. If validation fails, publishExpiry is never called — nothing is written.

  roomId,
  useCase: input.useCase,
  deadline: input.deadlineIso,

02 Hand out the links web

Two links come out: yours and theirs. Each carries only a room id and which side you are. Send theirs by whatever channel you already use; scan the QR with a phone if you are in the same room.

buildJoinUrl produces {APP_URL}/room/{roomId}?side=A|B. The QR encodes the same URL as a self-contained SVG (react-qr-code) — no external image service ever sees a room id. Two failure modes were found by rehearsing and are handled explicitly: the copy button silently does nothing off HTTPS because navigator.clipboard is undefined in a non-secure context, and a QR encoding localhost is unscannable from a phone, so the UI warns.

03 Write the position web

You write your terms in ordinary language — "I won't sell below €400,000, deed within 90 days". No forms, no dropdowns, no structured fields. A checklist beside the box reminds you which things usually matter for this kind of deal, but it never blocks you.

Free text is a deliberate choice. The moment you force people into fields, you have decided in advance what a deal can be about — and real negotiations always have a clause you did not anticipate.

The page is a Server Component that reads the room's expiry from Mirror to resolve the preset, then renders a client form. A room with no expiry on the topic cannot be written to at all (RNF-M1-001) — the clock must be public before any position exists.

src/app/room/[roomId]/write/page.tsx 
const topicId = requireEnv("HEDERA_TOPIC_ID");
const view = await createReader(hederaMirrorClient()).readSession(topicId, { roomId });
roomFound = Boolean(view.expiry);
useCase = view.expiry?.useCase ?? "property";

A privacy hole that lived in this form and was fixed: a <textarea name="position"> with default settings lets the browser save what you type to disk (form history is keyed by field name and offered as a suggestion later — even to the next person on that machine), and Chrome's Enhanced spell check or Edge's Microsoft Editor transmit the text to Google or Microsoft. Three lines above, the UI promises the words never leave the browser. The fix is autoComplete="off", spellCheck={false}, autoCorrect, autoCapitalize, data-1p-ignore, data-lpignore. This is a good story to tell: it shows the privacy claim is audited down to browser defaults, not just the cryptography.

04 One seat per side World

Before you can seal, you prove you are a person — and that you have not already taken this seat. Not a login: we never learn your name, your wallet or your face. What comes back is one opaque number that is the same if you come back, and different for anyone else.

Why it matters: without it, someone opens ten rooms and plays twenty questions with your number. "Workable at 400k? At 420k?" Six rooms and they have you. One seat per side ends that.

The nullifier is derived from (app_id, action, person). Getting the scope right is the whole design: per app would mean a person can use Overlap once ever; per room and side means they can negotiate freely but submit once per side per room.

}

05 Seal in the browser 0G key

Your words are encrypted on your own machine, before anything is sent. What travels over the network is a scrambled blob. Even if someone recorded every byte between your laptop and us, they would have nothing readable.

This is what protects the waiting period — and the waiting period is the dangerous part. Side A might write today and side B tomorrow. For all those hours, A's terms are sitting somewhere. If they sat there in the clear, we could read them before B had even written, which is precisely the advantage the product claims to abolish.

Hybrid encryption (ECIES): a fresh ephemeral keypair per seal → ECDH against the enclave's public key → HKDF-SHA256 to derive a 32-byte AES key and a 12-byte IV → AES-256-GCM over the UTF-8 plaintext, with the payload header bound as additional authenticated data. Full walkthrough in §7.

src/seal/seal.ts · the core 
const ephemeralSecret = opts.ephemeralSecret ?? kem.randomSecret();
const epk    = toHex(kem.publicKey(ephemeralSecret));
const shared = kem.sharedSecret(ephemeralSecret, recipient);
const { key, iv } = deriveKeyAndIv(shared, suite, epk);

const header = { v: SEAL_VERSION, suite, epk } as const;
const cryptoKey = await subtle().importKey("raw", buf(key), "AES-GCM", false, ["encrypt"]);
const ciphertext = new Uint8Array(
  await subtle().encrypt(
    { name: "AES-GCM", iv: buf(iv),
      additionalData: buf(headerAad(header)), tagLength: GCM_TAG_BITS },
    cryptoKey,
    buf(new TextEncoder().encode(plaintext)),
  ),
);

Sealing is randomised on purpose, and this was a deliberate reversal of the module spec's literal wording. "Same plaintext ⇒ same ciphertext" would leak equality of plaintexts on a public log, and let an attacker confirm a guessed position offline by comparing commitments. A unit test asserts two seals of the same text differ, so nobody "fixes" it back.

06 Commit Hedera

A fingerprint of your sealed blob — not the blob — goes onto Hedera's public log, along with your seat proof and whether you agree to the extra detail in the answer. From that moment you cannot change what you wrote: any different text would produce a different fingerprint, and the old one is on a log nobody can edit.

The commitment is sha256 of the ciphertext bytes, 64 lowercase hex. Hashing the hex string instead would be self-consistent but would silently disagree with any third-party verifier doing the obvious thing.

src/seal/seal.ts · line 166 
// Hash the ciphertext BYTES, not the hex string.
const commitment = toHex(sha256(ciphertext));

  type: z.literal("commitment"),

The server does not trust the client's commitment: submitCommitmentAction recomputes it from the ciphertext it received, claims the World seat (fail closed) before any write, and only then publishes.

src/registry/write.ts 
async publishCommitment(message: CommitmentMessage) {
  const valid = commitmentMessageSchema.parse(message);
  return client.submit(canonicalize(valid));
},

gapOptIn is required in the builder but defaulted in the schema. That asymmetry is intentional: a writer must pass an explicit choice, while a legacy message without the field reads as false. Missing consent fails safe to the bare verdict, never to disclosure.

07 The reveal fires orchestration

When the deadline passes and both sides have committed, the sealed envelopes are opened and handed to the referee. This is the step that turns a countdown into an answer — and until very recently it did not exist, which meant the product had six good parts and no result.

runReveal is a pure orchestrator: every collaborator is injected, so all of the fail-closed branches are testable without Hedera, 0G or a wallet. It reads the topic, refuses if a verdict already exists, derives consent, fetches the ciphertexts, unseals, evaluates, verifies the attestation, and only then publishes.

src/reveal/run-reveal.ts · the chain 
if (room.hasVerdict) return fail("already_published");
if (!room.hasExpiry)  return fail("no_expiry");

const hasA = room.commitments.some((c) => c.side === "A");
const hasB = room.commitments.some((c) => c.side === "B");
if (!hasA || !hasB) return fail("incomplete_commitments", `A=${hasA} B=${hasB}`);

// Consent from the TWO COMMITMENTS on the topic — never from the create form.
const consent = consentFromCommitments(room.commitments);

const sealed = await deps.sealedPayloads(input.roomId);
if (!sealed.a || !sealed.b) return fail("missing_sealed_payload", …);

[positionA, positionB] = await Promise.all([
  deps.unseal(sealed.a), deps.unseal(sealed.b),
]);

const evaluation = await deps.evaluate({ positionA, positionB,
  useCase: room.useCase ?? DEFAULT_USE_CASE, consent });
if (!evaluation.ok) return fail("evaluation_failed", …);
src/session/consent.ts · two-sided, fail-safe in every direction 
function sideConsented(commitments: CommitmentMessage[], side: Side): boolean {
  const own = commitments.filter((c) => c.side === side);
  // No commitment ⇒ not consented. Multiple ⇒ ALL must say true, so a stale or
  // forged duplicate can only downgrade to the bare verdict, never upgrade.
  return own.length > 0 && own.every((c) => c.gapOptIn === true);
}

An unseal failure reports the error type and nothing else. An AEAD failure message can carry fragments of what was being decrypted, so putting it in a log or a result object would leak a position through the error path. A unit test asserts a position never reaches the result.

  return fail("unseal_failed", error instanceof Error ? error.name : "unknown");

08 Sealed evaluation 0G

Both positions go to a model running inside the sealed hardware. It is told: read these two, and answer with exactly one word from this list. Nothing else. No explanation, no reasoning, no numbers.

The reason the answer is one word is not tidiness. The referee is the only thing that has seen both sides, so anything it says flows to both. A sentence of explanation would hand each side a piece of the other's terms.

Three switches are set explicitly on every request, and each one is a defect if left at its default: temperature: 0 (the provider default is 1), chat_template_kwargs.enable_thinking: false and reasoning_effort: "none" (this model returns chain-of-thought by default — confirmed live, 724 characters of it beside a one-word answer), and max_tokens: 16.

src/evaluator/og-request.ts 
export function buildChatRequest(input: ChatRequestInput): Record<string, unknown> {
  return {
    model: input.model,
    temperature: 0,
    max_tokens: input.maxTokens ?? DEFAULT_MAX_TOKENS,   // 16
    chat_template_kwargs: { enable_thinking: false },
    reasoning_effort: "none",
    response_format: input.responseFormat,
    messages: [
      { role: "system", content: input.system },
      { role: "user",   content: input.user },
    ],
  };
}

Receiving the reasoning is already the breach (D-M6-1). Not publishing it is not enough — a chain of thought discusses both positions in detail, so the moment it arrives, the operator has been handed what the privacy policy says they cannot have. So the check runs before the verdict is read: a correct verdict alongside a reasoning trace is still a failure.

src/evaluator/evaluate.ts 
// Checked BEFORE the verdict is read.
if (response.reasoningContent !== undefined && response.reasoningContent.trim().length > 0) {
  return fail("reasoning_returned",
    `${response.reasoningContent.length} chars of reasoning — thinking is not disabled`);
}

The prompt, and why the vocabulary depends on consent

When both sides have not opted in, gap:* is not merely rejected on the way out — it is never offered. The model is not asked to compute something it must not report.

src/evaluator/verdict.ts 
export const VERDICTS = ["workable", "not_workable", "gap:single", "gap:multiple"] as const;

export function applyConsent(verdict: Verdict, consent: GapConsent): Verdict {
  if (!isGapVerdict(verdict)) return verdict;
  return bothConsented(consent) ? verdict : "not_workable";
}

Why enforce consent twice? The prompt already asks for a bare verdict when consent is missing — but a prompt is a request, and this is a privacy boundary. Models do not always comply. So the rule is enforced on the way out too, where compliance is not required.

And why degrade rather than error? gap:* means "not workable, and here is how concentrated the problem is". Dropping the refinement leaves a verdict that is still true, just less informative. Failing the whole evaluation would punish both sides because one of them declined to share more — exactly the choice we promised to honour.

One more refusal worth knowing about: parseVerdict will not dig an enum value out of a sentence. If the model wrote a paragraph containing the word "workable", that is a compliance failure and must surface as one. Recovering a verdict from prose would make the enum guarantee true in the type system and false in reality.

09 Attestation 0G our crypto

The referee signs what it did with a key that lives inside the sealed hardware. We check that signature ourselves, using ordinary cryptography libraries — not 0G's code. If it does not match the key we pinned in advance, no verdict is published at all. The room ends with nothing rather than with something we cannot vouch for.

This is the load-bearing claim of the whole product, so the check is deliberately boring and deliberately ours.

The signature is not in the chat response. It is fetched separately, keyed by chatID, and what is signed is the string sha256(input):sha256(response) — so the signature covers the inputs as well as the output. That is what supports the claim "this model saw these inputs and returned this verdict".

src/evaluator/og-signature.ts 
export function signatureUrl(baseUrl: string, chatId: string, model: string): string {
  const base = baseUrl.replace(/\/v1\/proxy\/?$/u, "").replace(/\/$/u, "");
  return `${base}/v1/proxy/signature/${encodeURIComponent(chatId)}?model=${encodeURIComponent(model)}`;
}

Two traps encoded in that one function, both of which cost us real time:

① getServiceMetadata() returns an endpoint that already ends in /v1/proxy. Append the signature path to it and you get /v1/proxy/v1/proxy/… and an "unsupported endpoint" error that reads like a wrong route rather than a doubled prefix.

② A wrong path returns 404 page not found; a wrong chatID returns a business error. Same status family, completely different fix — which is why the code keeps the body on failure.

src/evaluator/og-signature.ts · building the envelope 
envelope: {
  payload: parsed.text,
  // LOAD-BEARING: 0G signs the text as a RAW STRING. Canonicalising it wraps it
  // in JSON quotes, the bytes stop matching, and it fails as `signer_mismatch` —
  // which is indistinguishable at a glance from a wrongly pinned key.
  encoding: "utf8",
  signature: parsed.signature,
  scheme: DEFAULT_SCHEME,             // secp256k1-eth  (EIP-191)
  model: input.model,
  attestationRef: url,
}
src/evaluator/attest.ts · the check itself 
// The response CLAIMS a signer. Evidence, not authority — we recover it ourselves.
if (envelope.signer !== undefined) {
  const claimed = stripHex(envelope.signer).toLowerCase();
  if (claimed.length > 0 && claimed !== pinned) {
    return fail("signer_mismatch", `envelope claims 0x${claimed}, pinned 0x${pinned}`);
  }
}

switch (envelope.scheme) {
  case "secp256k1-eth":
  case "secp256k1-raw":
    if (pinned.length !== 40) {
      return fail("malformed_signer", `expected a 20-byte address, got ${pinned.length / 2} bytes`);
    }
    return verifySecp256k1(envelope.scheme, signature, message, pinned);
  case "ed25519":
    return verifyEd25519(signature, message, pinned);
}

The result is a discriminated union, not a boolean, and that is on purpose: a bare boolean invites if (!res) to be forgotten. Note that { verified: false } is itself truthy.

src/evaluator/attest.ts · the gate 
export type AttestResult =
  | { verified: true;  scheme: SignatureScheme; signer: string }
  | { verified: false; reason: AttestFailure; detail?: string };

export function mayPublish(result: AttestResult): result is Extract<AttestResult, { verified: true }> {
  return result.verified === true;
}

Fail closed is enforced in the type system, not by discipline. buildVerdictMessage requires an attestationRef, and only a verified envelope produces one. There is no path from a failed attestation to a published verdict — you cannot even construct the message.

src/reveal/run-reveal.ts 
const fetched = await deps.attestation();

const attested = verifyEnvelope(fetched.envelope, deps.pinnedKey);
if (!mayPublish(attested)) return fail("attestation_invalid", …);

7 · Cryptography in detail

This is where the hardest questions land, so it gets its own section.

Sealing — ECIES, step by step

You want to write a message only one specific recipient can read, and you have never met them — you only know their public key. You cannot use a shared password, because there isn't one.

The trick: you generate a brand-new throwaway keypair just for this one message. Your throwaway private key plus their public key produces a secret number. Their private key plus your throwaway public key produces the same secret number. So you encrypt with it, send along your throwaway public key in the clear, and only they can reproduce the secret and decrypt.

The four decisions inside that diagram

① The IV is derived, not random and not zero. The AES key is unique per seal because the ephemeral keypair is fresh, so nonce reuse — the classic way to destroy GCM — is impossible by construction.

src/seal/seal.ts · deriveKeyAndIv() 
const info = new TextEncoder().encode(`seam/seal/v${SEAL_VERSION}|${suite}|${epkHex}`);
const okm  = hkdf(sha256, sharedSecret, undefined, info, AES_KEY_BYTES + IV_BYTES);
return { key: okm.slice(0, AES_KEY_BYTES), iv: okm.slice(AES_KEY_BYTES) };

② The ephemeral public key goes into the HKDF info. Substitute the epk and a different key is derived, so decryption fails rather than quietly succeeding on attacker-chosen material.

③ The header is bound as AEAD additional data, and it covers the suite tag — so the suite cannot be downgraded without the GCM tag check failing.

src/seal/seal.ts · headerAad() 
export function headerAad(header: Omit<SealedPayload, "ciphertext">): Uint8Array {
  return new TextEncoder().encode(canonicalize(header));
}

④ The suite is tagged in the payload, never inferred. Which key the enclave would decrypt with is still an open question, so tagging makes the answer a data change rather than a rewrite.

src/seal/suites.ts 
export const SEAL_SUITES = [
  "x25519-hkdf-sha256-aes256gcm",
  "secp256k1-hkdf-sha256-aes256gcm",
] as const;

export const DEFAULT_SUITE: SealSuite = "x25519-hkdf-sha256-aes256gcm";

The secp256k1 validator carries a hint that exists because of a real confusion — and it is worth quoting in the Q&A, because it explains why the attestation key cannot double as the sealing key:

if (key.length !== 33 && key.length !== 65) {
  throw new Error(
    `secp256k1 public key must be 33 or 65 bytes, got ${key.length}` +
      (key.length === 20 ? " — that looks like an ADDRESS; you cannot encrypt to an address" : ""),
  );
}

Canonical serialisation — why one function, in one file

A signature is over bytes, not over "the data". If the signer and the checker turn the same information into even slightly different bytes — a space, a different key order — the signature will not match, and you cannot tell that from a genuine forgery.

RFC 8785 (JCS) in spirit, restricted to the subset Overlap actually uses, hand-written so it audits in one screen with no dependency. Keys sorted by UTF-16 code unit recursively · compact JSON · UTF-8 with NFC-normalised strings · array order preserved · undefined dropped, null kept · integers only.

Two of those rules are less obvious than they look:

  • NFC normalisation. "é" as one code point and as "e" plus a combining accent are the same string to a human and must be the same bytes to a verifier.
  • No floats. Their textual formatting is not portable across runtimes. We never need one, so they throw.
src/lib/canonical.ts 
if (!Number.isInteger(value)) {
  throw new NotCanonicalError(`floats are not canonical: ${value}`);
}
// -0 and 0 are the same value; only one spelling may reach the bytes.
return Object.is(value, -0) ? "0" : String(value);

And the exception that proves the rule. 0G signs its text as a raw string. Canonicalising it would wrap it in JSON quotes, changing the bytes, and the check fails as signer_mismatch — which looks exactly like a wrongly pinned key and is not one. Hence encoding: "canonical" | "utf8" on the envelope, and a test that asserts the real signature fails under canonical so the trap stays caught.

Verifying the signature — the five steps

  1. Take the raw bytes of the signed text.
  2. Apply EIP-191 framing: \x19Ethereum Signed Message:\n<len> + message, then keccak256.
  3. Recover the public key from (r, s, v) with @noble/curves.
  4. Address = last 20 bytes of keccak256 of the uncompressed key minus its 0x04 tag.
  5. Compare case-insensitively with the pinned OG_ENCLAVE_PUBKEY.

Malleability is rejected too — a signature with a high s value fails as malleable_signature, so the same message cannot have two valid signatures.

9 · What we prove, and what we don't

Read this section twice. A demo that overstates its guarantees loses to a single question. Every limitation below is one we found ourselves and chose to state — which is a much stronger position than being shown it.

① We verify the last link, not the whole chain

We check that the answer was signed by the key we expected. We do not check the hardware's own certificate all the way back to Intel.

Say it like this: "We pin the enclave's signing address and verify the response signature ourselves, with general-purpose crypto and no 0G code in the trust path. We do not parse the TDX quote or walk the cert chain to an Intel root — that was out of scope for the weekend."

Do not say: "fully attested" or "hardware-verified end to end".

② The unsealing happens on our server

The browser encrypts, but our server opens the envelope just before handing the text to the model — because 0G's inference API is a chat endpoint with nowhere to put a decryption key.

Say it like this: "Sealing is real and in the browser. But 0G's inference API is a chat endpoint — there is no way to hand it a private key and have it decrypt inside the enclave, and the only key it exposes is a 20-byte signing address you cannot encrypt to. So today our server unseals in memory immediately before the call. We have asked 0G for an enclave encryption key; if it exists, this becomes a config change."

Never say: "plaintext only ever exists inside the TEE."

Verified in the SDK, so you can say it with confidence: the inference path has no request-body encryption at all, and the only ECIES helper lives in fine-tuning and runs the other way — the trained model comes back encrypted to the user's wallet.

③ The ciphertext window between commits is in-memory

Side A can commit and side B follow minutes later. Hours or days would not survive a server restart today.

src/app/room/[roomId]/write/actions.ts 
const sealedByRoom = new Map<string, SealedPayload>();

Say it like this: "No database is a design constraint, so the sealed payloads sit in process memory between commits. For a demo that is fine; for the real thing they belong on the topic as ciphertext, which is a scoped change we chose not to make before the freeze. The trade-off is that ciphertext on a public ledger is forever, so a future key compromise would expose past positions — with hashes only, it cannot."

④ armReveal is not wired at room creation

The module exists and is tested, but nothing calls it yet, and that was deliberate: hederaScheduleService(buildRevealTx) needs a transaction for Hedera to execute at the deadline, and the only meaningful one is a topic message marking that the clock fired — a fourth message type, which decodeMirrorMessage throws on, which would break every read of every room.

Say it like this: "The deadline is enforced against the expiry we published to the topic before anyone could write, so neither side can move it — which is the property the schedule was there to provide. Wiring the scheduled transaction itself needs a fourth message type and topic versioning, and we scoped that rather than break the read path the night before."

⑤ Selfie Check vs the v2 fallback

Selfie Check is 4.x only (selfieCheckLegacy). If the shipped build requests VerificationLevel.Device, it is running device verification and not Selfie Check.

Check which one you are demoing before you say the word. If it is the v2 fallback, say so plainly and point at the friction log — a beta track rewards an honest report. Claiming Selfie Check while running device verification is the one version of this that damages you.

⑥ We picked a deliberately weaker model

0gm-1.0-35b-a3b has one provider, so the enclave signing key cannot rotate out from under our pin. glm-5.2 is stronger and has three.

Say it like this: "When the product is 'we can prove who signed this', a stable signer is worth more than a smarter model." This is a good answer — invite the question.

⑦ The model reads the plaintext. Obviously.

It has to, to judge it. What the TEE provides is not "nobody sees it" but "no operator can", because the hardware denies it to the machine's own owner. Get this distinction right and the whole story holds together; get it wrong and it sounds like magic, which invites disbelief.

10 · Hard questions

Ranked by how likely you are to be asked. See also agente/judging-qa.md.

"So you can read both positions, right?"

"Not from the topic — that holds only hashes, and npm run inspect shows it. In the current build there is one moment where our server holds the plaintext, between decrypting and calling the enclave, because 0G's inference API is a chat endpoint with nowhere to put a decryption key. We say that out loud rather than hide it. Everything else is sealed in the browser."

"How do I know the model really ran in a TEE?"

"You do not have to take our word for it. The provider's teeSignerAddress is on 0G mainnet — here is the eth_call. The response signature is fetched from the broker by chatID and we verify it with @noble, not with 0G's SDK. Run npm run spike: it verifies a real signature and then flips one character and shows it rejected. What we do not do is parse the TDX quote to an Intel root."

"What if the enclave signature is invalid?"

"Nothing is published. Not a fallback verdict, not a 'probably fine' — nothing. And it is not enforced by discipline: buildVerdictMessage requires an attestationRef that only a verified envelope produces, so a verdict message with a bad attestation cannot be constructed."

"Where does the other party agree to the gap disclosure?"

"On their own commitment message, on the topic. consentFromCommitments requires both. Consent never comes from the create form — that is only side A's preference. And if a side somehow has two commitments, all of them must say yes, so a stale or forged duplicate can only downgrade to the bare verdict."

"Why not tell them which dimension blocks? It would be more useful."

"Because 'the timing blocks' also says 'your price was acceptable', and the other side walks into the next call knowing it. We designed that version and rejected it: 'the single blocking dimension' is ill-defined when several block or when tradeoffs entangle them, so a forced pick would fabricate an answer and leak more than a count. So we report how many, never which."

"What stops me opening ten rooms and guessing your number?"

"World, one seat per room per side, scoped by action. That attack is exactly why World is in the stack — it is not a login feature, it is the control that makes the one-word answer safe to give."

"You have no database. Where does anything live?"

"The HCS topic is the database — three versioned message types, append-only, consensus-ordered, and readable by anyone through Mirror Node without our server. The one exception is the ciphertext between commits, which is in process memory; see the limitation we listed."

"Is this just a wrapper around an LLM call?"

"The LLM call is four lines. The product is everything around it: the output vocabulary is closed so the referee cannot leak by talking, consent is two-sided and read from the ledger, the response signature is verified outside the vendor's SDK and the publish path fails closed, and sealing is randomised so identical positions do not produce identical commitments. Remove any one of those and the privacy claim stops being true."

"Why Hedera and not just a database?"

"Because 'we promise we did not change the deadline' is worth nothing. The clock is published before anyone can write, on a log we cannot edit, that both parties can read without us. A database would put us back in the middle — which is the position the product exists to eliminate."

"What would you do with another week?"

"Three things, in order. Get the enclave encryption key so the unsealing moves inside the TEE and the seam in §9② closes. Put the ciphertext on the topic so the two sides can be days apart instead of minutes. Then parse the TDX quote properly so the attestation is the full chain and not just the last link."

Built from the code, not from memory — every snippet was read out of the repository at the path shown above it. If a file has moved since, the code wins and this document is wrong.
